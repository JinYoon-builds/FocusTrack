# Tech Note: 커넥션 풀(Connection Pool)과 서버리스의 한계

## 1. 커넥션 풀(Connection Pool)이란?

### 🚕 비유: 택시 승강장
* <b>커넥션(Connection):</b> 손님을 태우기 위해 택시를 <b>"호출"</b>하는 행위.
* <b>문제점:</b> 매번 택시를 부를 때마다 기사님이 집 앞까지 오는 데 10분씩 걸림(Handshake 비용). 손님이 1초 만에 내리는데, 부르는 데 10분이 걸리면 비효율적임.
* <b>해결책 (Pooling):</b> 아예 택시 10대를 건물 앞에 <b>"미리 대기(Standby)"</b> 시켜둠.
    * 손님이 오면? → 대기 중인 택시 타고 바로 출발.
    * 내리면? → 택시를 보내지 않고 다시 대기 줄로 복귀.
    * <b>결과:</b> 기다리는 시간(Latency)이 0에 수렴함.

### 💻 기술적 정의
데이터베이스(DB)와 애플리케이션 간의 <b>연결(Session)</b>을 맺는 과정(TCP Handshake + 인증)은 리소스 소모가 매우 크다.
따라서, 웹 서버가 실행될 때 <b>미리 일정 개수(예: 10개)의 DB 연결을 생성</b>하여 메모리 공간(Pool)에 보관해 두고, 요청이 들어오면 빌려주고 반납받는 방식을 말한다.

---

## 2. 커넥션 풀 고갈(Exhaustion) 문제

### 💥 상황 발생
* 우리 가게(웹 서버)의 택시 승강장에는 택시가 <b>10대(Max Pool Size)</b> 뿐이다.
* 그런데 갑자기 <b>손님 100명(Concurrent Request)</b>이 동시에 들이닥쳤다.

### 🚫 결과
1.  손님 10명은 택시를 타고 나감.
2.  나머지 90명은 택시가 돌아올 때까지 <b>무한 대기(Blocking)</b>.
3.  기다리다 지쳐서 "에라이 안 먹어!" 하고 떠남 (<b>Time-out 에러 발생</b>).
4.  이것이 바로 <b>"커넥션 풀이 말랐다(Exhausted)"</b>는 상황.

---

## 3. 왜 서버리스(Lambda)에서 이 문제가 심각한가?

일반 서버(EC2)와 달리, 서버리스(Lambda)는 <b>"고립된 실행 환경"</b>을 가진다. 이 구조적 차이가 치명적인 문제를 만든다.

### 🅰️ 일반 서버 (EC2 / Django, Spring)
* <b>구조:</b> 하나의 거대한 서버 프로세스가 <b>하나의 커넥션 풀(택시 10대)</b>을 관리함.
* <b>효율:</b> 사용자 1,000명이 와도, 서버가 알아서 줄을 세워서 택시 10대를 돌려막기(Reuse)함.
* <b>DB 부하:</b> DB 입장에서는 연결이 10개만 맺어져 있으므로 평온함.

### 🅱️ 서버리스 (AWS Lambda)
* <b>구조:</b> 요청이 들어오면 AWS가 <b>새로운 컴퓨터(컨테이너)를 띄움.</b>
* <b>문제:</b>
    * 사용자 100명이 동시에 접속함.
    * AWS가 <b>Lambda 함수 100개를 동시에 실행</b>함.
    * 각 Lambda는 서로 남남임. (메모리 공유 불가)
    * 각자 "나 DB 연결할래!" 하고 <b>새로운 커넥션을 1개씩 맺음.</b>
* <b>결과:</b>
    * 순식간에 <b>DB 연결 요청이 100개, 1,000개로 폭증.</b>
    * MySQL 같은 RDBMS는 보통 동시 연결 수(Max Connections) 제한이 있음 (예: 100개).
    * <b>101번째 Lambda부터는 DB가 "자리가 없어(Too many connections)"라며 쫓아냄.</b>
    * <b>시스템 전면 장애(Downtime) 발생.</b>

---

## 4. 해결책: 왜 DynamoDB인가?

이 문제를 해결하려면 RDBMS 앞에 'RDS Proxy' 같은 중계기를 둬야 하는데, 비싸고 복잡하다.
반면, <b>NoSQL(DynamoDB)</b>는 접근 방식이 근본적으로 다르다.

* <b>RDBMS:</b> 전화기 들고 통화 연결(Connection)을 유지해야 대화 가능. (Stateful)
* <b>DynamoDB:</b> 우체통에 편지(HTTP Request) 넣고 감. (Stateless)
    * 연결을 맺고 끊는 개념이 없음.
    * 그냥 API 요청(Request) 날리면 끝.
    * Lambda가 1,000개든 10,000개든 상관없이 <b>연결 고갈 문제가 발생하지 않음.</b>

### 🎯 결론 (Takeaway)
서버리스 아키텍처(FaaS)에서는 <b>Connection-less(비연결성)</b> 통신을 하는 <b>DynamoDB</b>가 궁합이 가장 좋다.
(만약 RDBMS를 꼭 써야 한다면, AWS RDS Proxy 같은 별도의 커넥션 풀링 서비스가 필수다.)
